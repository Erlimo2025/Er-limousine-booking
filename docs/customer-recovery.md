# Customer email password recovery

Recovery uses account email, not phone. Phone registration/storage and email/password login are unchanged. FIRST15 remains 15% and is independent of recovery.

Configuration: CUSTOMER_EMAIL_RECOVERY_ENABLED=false by default. To enable a reviewed deployment, provide RESEND_API_KEY privately, CUSTOMER_RECOVERY_FROM as a sender on erlimousineservice.com, and canonical SITE_URL. Production SITE_URL must be an HTTPS origin with no credentials, query, fragment or extra path. Enabled recovery with missing/invalid configuration prevents startup. Disabled recovery does not load the API key. Never print or paste credentials into files, logs or support reports.

The Resend adapter uses Node fetch to the fixed HTTPS send-email API with an eight-second abort timeout and a nonsecret attempt-based idempotency key. Sending happens after the generic HTTP response and outside database transactions. Raw provider errors/responses, email contents and links are never logged. No real provider is used in automated tests. A failed or ambiguous delivery remains fail-closed until a successful provider acknowledgment has been stored; customers may request another link subject to cooldown. A process crash before delivery can require a new request. There is no plaintext-token outbox and no automatic durable retry.

Request accepts normalized account email. Known, unknown and identity-throttled valid requests have the same generic response and no recovery cookie. Decoy challenges preserve uniform storage behavior without sending email for unknown accounts. Persistent limits: three request attempts per email hash/hour, twenty per client hash/hour, sixty-second send cooldown; HTTP limits: five sends, thirty exchanges and ten resets per minute/client. Repeated requests do not revoke usable links; password reset revokes all outstanding authority. Rate limits also apply to unknown identities.

Each emailed token is 32 cryptographically random bytes; only its SHA-256 hash is stored. Lifetime is ten minutes. A dedicated local-assets-only reset page reads the URL fragment, immediately removes it with history.replaceState, and holds the token briefly in memory. GET does not consume it. An explicit button submits a same-origin JSON POST to exchange it once for a different random HttpOnly, SameSite=Strict, Secure-in-production cookie restricted to /api/customer/recovery. Only the reset-cookie hash is stored. Exchange never extends the original deadline. The emailed token never enters cookies, persistent browser storage, API JSON responses or server request URLs.

No-store, no-referrer and restrictive CSP protect the reset page. No analytics, remote resources or application tracking are included. RESEND DOMAIN CLICK/OPEN TRACKING MUST REMAIN DISABLED. The send-email call does not claim to disable domain tracking per message; no domain-configuration API calls are made. Confirm those dashboard settings before activation. Email providers, mail-security scanners and mailbox holders necessarily receive the original emailed link; fragment removal cannot erase their copies. GET-only scanners cannot consume it, though scanners that explicitly execute and submit the page may do so. Never share a live reset link.

Migration 005 leaves 004 unchanged, adds email_link method and unique token-hash storage, permits absent SMS verifier only on email records, and adds email throttle scope. It transactionally invalidates all legacy SMS grants/challenges. It is idempotent under the existing advisory migration lock. No customer, booking or payment data is deleted. Legacy phone counters are inert. SMS recovery routes/provider have been removed.

Customer-before-challenge row locking serializes exchanges and reset across workers. Reset reuses scrypt, updates the password, deletes all customer sessions and consumes every outstanding recovery challenge in one transaction. Existing login hash rechecking prevents stale-password session creation after reset. Admin sessions are separate. Expired recovery metadata remains unusable pending a future reviewed retention job.

Current account emails are not enrollment-verified. Recovery proves possession of the stored mailbox, not prior identity enrollment. Typoed/unavailable mailboxes require a future reviewed support policy; no unsafe manual override or phone fallback exists. Mailbox compromise grants recovery authority. This work does not implement account-based FIRST15, email enrollment verification, profile editing or other account phases.
