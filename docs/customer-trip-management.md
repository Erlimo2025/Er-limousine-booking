# Customer trip management

My Trips adds a compact **Manage Trip** disclosure for an authenticated customer's own active reservation. Existing Book Again and Complete Payment actions remain separate. Capability flags and the pickup instant come from the server; the browser clock, displayed address, email, phone and reservation ID alone never grant authority.

## Pickup date/time changes

`POST /api/customer/trips/:id/pickup-time` changes only the outbound pickup date/time and its authoritative schedule columns. The request contains `date`, `time`, `expectedPickupAt`, a generated `requestId` UUID and strict `confirmed: true`. The UI requires a labeled New York date/time selection and an explicit confirmation before submission.

Paid and unpaid reservations can change their pickup time independently of the cancellation cutoff, including inside 24 hours. Cancelled/completed reservations and reservations whose scheduled service end has passed cannot be edited. The new pickup must be valid and future relative to server time. Scheduling uses `America/New_York` and the application's existing parser: nonexistent DST times are rejected, and existing ambiguous-time semantics are preserved. The UI does not establish eligibility.

For round trips, the return pickup remains fixed; the new outbound pickup must precede it. For hourly trips, the schedule end moves with the new pickup while retaining the booked duration. Vehicle, route, passengers, flight data, fare, discounts, FIRST15, EWR qualification, reservation ID and payment state are unchanged. The action does not calculate a quote, create Checkout, charge a card or request a refund.

An unpaid time change also reconciles the current payment attempt under the existing reservation action lock. A safely reusable open/unpaid Checkout session is expired and the old attempt is retired before the schedule update is committed. The time change creates no replacement Checkout: the next Complete Payment action creates a fresh session with the new pickup description and the unchanged stored fare. Already expired/unpaid evidence can be retired without another payment submission. Unknown, paid or in-progress provider evidence fails closed; it cannot authorize a schedule change or a second payment attempt. A lost session-expiration response can be reconciled on a later retry. Paid time changes never create or modify Checkout merely to update the schedule.

Cancellation eligibility is recalculated from the newly stored pickup instant immediately after a time change. Moving pickup from 30 hours away to 10 hours removes online cancellation; moving it from 10 hours away to 30 hours restores eligibility when all other rules permit it.

## Free cancellation and payment safety

`POST /api/customer/trips/:id/cancel` accepts `expectedPickupAt`, `requestId` and strict `confirmed: true`. The UI presents a separate cancellation confirmation; paid customers explicitly confirm cancellation and a full-refund request. The server permits self-service cancellation at **24 hours or more** before pickup, including exact equality. Eligible unpaid trips are cancelled without a refund; eligible paid trips enter the durable full-refund flow below. Just under 24 hours is rejected and customers are directed to the existing company phone/email. Comparisons use elapsed milliseconds between authoritative instants, including across DST transitions.

Cancellation and payment actions use the existing reservation action lock. If another worker holds it, the mutation returns a retryable conflict. Unpaid cancellation re-reads the owned reservation under that lock and validates/expires any open Checkout session before accepting a safe unpaid proof. Provider-paid/processing, unknown or ambiguous submission evidence fails closed. The final row-locked transaction checks the proof against the exact stored session, marks the reservation Cancelled and releases FIRST15 claims atomically only after safe unpaid cancellation. Paid cancellation preserves the paid FIRST15 eligibility claim and establishes a refund operation atomically. Complete Payment is unavailable after either accepted cancellation.

The signed Stripe webhook remains the only Paid authority. If payment arrives after an unpaid cancellation, existing cancelled-but-paid handling preserves Cancelled status and payment evidence, sets operator-review state and gives accurate support-review messaging. That late-payment path does not automatically create a refund or silently re-confirm the trip.

## Paid cancellation and full refunds

An eligible paid owner can request cancellation and a full refund from My Trips. The browser supplies only the owned reservation reference, schedule precondition, request UUID and confirmation; it never chooses the Stripe payment, customer or refund amount. The server verifies the stored paid reservation, signed-payment ledger association and the provider's captured payment/charge. Session, PaymentIntent, charge, amount and currency must consistently identify that reservation's actual authoritative captured payment. Existing/partial refunds, inconsistent evidence or unverified payment source do not produce a new refund request.

Cancellation, immutable customer audit and one durable refund operation are committed together. Migration 009 stores a reservation-unique refund operation with server-generated UUID/idempotency key, original session/payment/charge association, authoritative amount/currency, submission timestamps, provider refund association and fixed states/evidence. A separate append-only refund-evidence history preserves submission, ambiguity and webhook outcomes. No card data, client secret or raw provider payload is stored. All provider submission/retrieval happens outside long database transactions under the reservation action lock.

Before refund submission, the durable operation records that submission may have occurred. Repeated Cancel actions and worker restarts reuse the same operation, immutable provider parameters and Stripe idempotency key. A lost response stays submitted/unknown; a subsequent provider error cannot erase that ambiguity or permit another refund operation. An identified refund is retrieved/reconciled by its recorded association. Unidentified ambiguity beyond the conservative 23-hour idempotency retry window stops automatic submission and requires operator review. There is no alternate key or second refund attempt to work around an unresolved outcome.

**Only a signed, association-validated Stripe refund webhook reporting `succeeded` establishes refund confirmation.** A create/retrieve API response, browser return, request success or a pending provider refund cannot establish “Refund confirmed.” Webhook handling uses the reservation action lock and a bounded retrieval of the current recorded Stripe refund, then verifies the application operation and reservation, refund/payment/charge identities, exact amount and currency. A delayed/out-of-order event cannot overwrite newer provider evidence merely because its payload claims an older status. Confirmed/failed webhook reconciliation is idempotent and atomically records evidence plus the distinct outbox events when appropriate.

Stripe can report a later refund failure after earlier success evidence. An association-validated signed event plus matching current provider failure/cancellation moves the displayed refund to operator review while retaining the historical confirmation/evidence. It does not create a second refund or restore the trip. Pending/retryable refund-confirmation outbox jobs are retired so an obsolete frozen confirmation is not retried, and one customer/admin refund-review correction pair is queued. An already delivered confirmation remains a historical event; the correction explains the current review requirement without exposing provider/bank details. Operator review never asserts that the refund is complete.

Reservation status remains Cancelled and payment history remains Paid; refund status is separate. My Trips shows refund processing, refund confirmed or contact/operator review as appropriate and never offers another Complete Payment action. Cancellation emails distinguish acceptance/processing from confirmed refund; confirmed-refund emails are queued only after authoritative confirmation. Banks may take additional time to display a confirmed refund. Failed/ambiguous refunds do not restore the reservation or imply a completed refund.

## Ownership, replay and audit

Mutations require the existing active customer session, canonical Origin, safe Fetch Metadata and JSON, with client and shared account rate limits. Full source lookup is relational `customer_id + reservation ID`; guest credentials do not grant this authenticated management feature. The database rechecks the active account/session under lock before mutation.

The pickup instant is an optimistic concurrency precondition. Stale submissions return a conflict and the UI refreshes authoritative trips. Identical retry submissions retain the same request UUID. Reusing a request UUID for different data is rejected; a valid recorded replay returns without mutating the reservation or creating another email event. Repeated cancellation of an already cancelled owned reservation is safe.

Migration **009-customer-trip-management.sql** creates immutable `er_customer_trip_events`. Each event stores its UUID, reservation UUID, customer UUID, request UUID, event kind, old/new pickup and service-end instants, change details and server timestamp. Unique request scope prevents duplicate audit entries. The application changes the reservation, writes the event and queues emails in the same transaction. Audit history cannot be updated/deleted through ordinary database writes. The same uncommitted migration includes the refund-operation/evidence support and refund email kinds. Migrations 001–008 are unchanged.

## Email events

The existing Resend provider and durable booking-email outbox deliver two emails for each successful mutation:

- Time change: customer **Pickup Time Updated | ER Limousine Service**, plus ER Limousine notification, with the old/new pickup date/time, reservation reference and route. The operator message includes existing stored customer contact details.
- Cancellation: customer **Trip Cancelled | ER Limousine Service**, plus ER Limousine notification with the stored trip details. An accepted paid cancellation says the refund is processing; ambiguous/failed outcomes direct the customer to operator review. Wording does not assert an unverified refund.
- Full refund confirmation: customer **Refund Confirmed | ER Limousine Service**, plus ER Limousine notification, linked to the original cancellation audit. Only the authenticated signed-refund webhook transition can queue this separate pair.
- Refund review/correction: customer **Refund Review Required | ER Limousine Service**, plus ER Limousine notification, linked to that same cancellation audit. The server queues this pair once for an authoritative review transition; the message preserves Cancelled status and requests contact without provider details or an unverified refund-completion claim.

Migration 009 adds an event reference to the outbox and separate uniqueness for original booking/payment events versus mutation events. This preserves the four existing booking/payment email events while allowing multiple distinct time changes. Event-specific snapshots retain the correct old/new schedule even if later edits occur before delivery. Provider submission remains outside the mutation transaction, with existing leases, frozen payloads, idempotency and retry handling. Resend failure cannot undo a successfully committed mutation.

## Browser behavior and scope

Mutation and list responses are no-store/no-referrer. Management UI uses safe text rendering and validated `tel:`/`mailto:` company links, 44px controls and mobile-friendly disclosure layout. Double submissions are blocked. Account/trip generations guard success, errors, 401 handling and list refresh; stale responses cannot clear or overwrite a newer authenticated view. Current-generation authentication failure clears private state and uses the existing login flow.

No pricing, authentication, saved-card, guest booking, Book Again, Pay Now/Pay Later, reservation payment authority or Stripe webhook signature behavior is redesigned. Automated verification uses only mocked providers and isolated local PostgreSQL. Before production use, Stripe Sandbox verification must confirm capture/refund associations, required refund webhook delivery/signatures, card/network refund state changes, lost-response retry behavior and the customer/bank settlement messaging. No live Stripe call or production configuration change is part of local implementation.
