# Automatic booking emails

The existing server-only Resend adapter in services/email.js sends both password recovery and booking messages. It keeps the verified erlimousineservice.com sender, existing RESEND_API_KEY/CUSTOMER_RECOVERY_FROM configuration, canonical SITE_URL validation, eight-second timeout and sanitized failures. There is no second provider, SDK or card/payment email system.

BOOKING_EMAILS_ENABLED can explicitly enable/disable booking delivery. When absent it follows the existing CUSTOMER_EMAIL_RECOVERY_ENABLED setting, so an already configured Resend installation can send automatically. Booking-only configuration does not enable password recovery. Disabled or invalid booking-only email configuration does not prevent reservations/payments. No production variables are changed by implementation. Admin recipient/support contact reuse COMPANY_EMAIL and COMPANY_PHONE, with the same site defaults. Never put real credentials into .env.example, logs or support reports.

Migration 008 creates a dedicated PostgreSQL outbox, under the existing migration transaction/advisory lock. Migrations 001–007 are unchanged. Reservation creation atomically queues separate reservation_created (ER Limousine) and customer_reservation_created jobs; FIRST15/creation rollback also rolls back the job. Only the signed Stripe webhook's first Paid transition atomically queues payment_confirmed (customer) and admin_payment_confirmed. Browser returns and API reconciliation cannot queue Paid confirmation. Duplicate webhook events do not create another job; UNIQUE(booking_id,kind) adds a second guard. Imported historical data is not backfilled.

Email sends happen outside reservation/payment transactions, after API actions release booking locks. Immediate kicks, a startup kick and a one-minute unref'd worker timer recover pending deliveries. Each pass processes at most ten jobs. Short FOR UPDATE SKIP LOCKED claims and sixty-second leases coordinate workers. Failures back off from thirty seconds to one hour; they do not revert reservation state, payment state, ledger entries or FIRST15 claims. A database failure to atomically record state/outbox rolls back the whole transaction and lets the existing request/webhook retry safely.

Before submission, the exact allowlisted email message is frozen durably. A stable booking-email/<job UUID> Resend idempotency key handles retries and lost responses. Sent state prevents future sends, and a stale claim cannot finalize another worker's job. Resend retains keys for 24 hours; retries stop conservatively after 23 hours from first submission and enter review_required instead of blindly risking duplicates. No automatic re-send/reset or claim of absolute mailbox delivery is made. Review these exceptional cases in the provider dashboard before any separately approved manual action.

The outbox stores reservation reference/type and delivery bookkeeping, not Stripe payloads, API keys, reset/access tokens or card information. The temporary frozen payload contains only intended recipient, fixed subject and safe rendered message; it includes necessary reservation/contact PII, is inaccessible through customer/admin APIs, and is cleared on sent/review_required. Minimal sent metadata remains for deduplication and is deleted with its reservation via the FK. Existing database/backup access and retention policy also applies to these temporary payloads.

Admin messages include authoritative stored trip/contact/flight/notes/fare/status and original Pay Now/Pay Later intent where known. Customer reservation messages are a separate event: unpaid reservations say “Reservation Confirmed — Payment Due”, explain that payment is still due, and include stored trip/reference/vehicle/authoritative total and Unpaid status. Only relationally owned reservations receive a canonical /account/dashboard My Trips link, with no reservation ID or credential in the URL. Guests receive no payment link or access credential; existing guest authorization remains unchanged. Payment Confirmed emails go separately to both customer and ER Limousine only after the signed webhook establishes Paid. Cancelled paid reservations receive explicit cancellation/payment-review wording, never trip reconfirmation or an automatic refund. All reservation text is escaped in HTML; no provider/session URLs, ownership IDs or token hashes are included. Operational logs contain only fixed diagnostic categories and generated reference IDs, never recipients, addresses, provider bodies or credentials.

Resend domain click/open tracking settings remain unchanged; retain the existing reviewed disabled tracking settings. Tests use mocked Resend/Stripe/Google and isolated TLS-verified PostgreSQL only. No live delivery is required for automated tests.
